# Powder detection: validation report

Five-agent verification, 2026-11-28. Four investigators (physics, live data, adversarial falsifier, alternative methods) plus this synthesis. Every claim below was re-checked against the code and the live file (`data/forecasts_v2.json`); line numbers were opened and confirmed. No code was changed.

## Verdict in one paragraph

The powder system's physics is honest and fails closed: every gate matches real powder science (cold during fall, no rain, no thaw, no wind-pack), every missing input blocks a claim rather than estimating one, and nothing we attacked produced a false powder call. But two of the Powder page's three sections are structurally dead, not strict: the fallen-snow groups ("Snow measured/reported, 3 days") can never list any resort because the fetcher nulls the past-day temperatures, gusts and powder temperature the retroactive gates require, and "powder today" (day 0) can never score because the previous day's rain risk is always null. Both defects are already written up in `docs/powder_fetcher_fixes.md` (items 3 and 6) and remain unimplemented. The "ratio" is exactly what the code says it is: Open-Meteo's fixed 7:1 snow-to-water factor, used correctly as a frozen-fraction check — but because it is fixed, the 10 cm amount gate systematically rejects the coldest, driest storms, the exact days a powder chaser wants. The forecast path itself works end-to-end: on the 12:12Z refresh, Palisades Tahoe day 3 lists as "powder" (11.6 cm, frozen fraction 0.92, q=2), the first live proof a row can pass all gates.

## What we verified works (with evidence)

**The frozen-fraction ratio is implemented as documented and is mathematically sound.** `SNOW_CM_PER_MM = 0.7` (`dashboard_v2/data.py:193`) matches Open-Meteo's own fixed factor — confirmed live against the API: hourly `snowfall_cm / frozen_mm` = 0.700 exactly, at every temperature from -4.5 C to -9.1 C. So `ff = snow / (0.7 × precip)` (`data.py:648`, `powder.py:163`) is a true frozen fraction of the day's water: across 39 snowy band-days in the live file, ff median 0.99, max 1.01, none above 1.05. The code's docstring (`data.py:589-594`) honestly says this measures frozen fraction, not density. Hand recomputation on 4 resorts matched the code to 3 decimals (Stevens Pass 0.446, Crystal 0.908, Jackson Hole 0.999, Shiga Kogen 0.998).

**The hourly phase split is conservative and well tested.** `hour_split` (`scripts/fetch_data_v2.py:2493-2514`) uses no air-temperature threshold at all: it is purely geometric (band elevation vs snow line) plus the model's own liquid/frozen split, explicitly rejecting the lapse-rate temperature as an inversion artifact. Liquid above the snow line is classed "mixed", never "snow". The below-freezing rain recount (`data.py:197-221`) fires only when the band sat at or above the day's *maximum* freezing level in every wet hour — stricter than the snow line itself. The fetcher phase layer has real tests (`tests/fetcher_v2/test_phase.py`: line-boundary, FL-250, water conservation).

**The snow line (freezing level − 250 m) is a defensible midpoint.** Literature puts the rain-snow transition 200-400 m below the freezing level. Where Open-Meteo supplies its own `snowfall_height`, the code uses it (`fetch_data_v2.py:2500-2508`); the fallback governs 141 of 168 wet short days (84%). The hard cutoff under-calls snow just below the line — the safe direction for a powder page.

**The gate set matches real powder physics, and the gates bite correctly on live data.** Forecast gates: band snow ≥ 10 cm, ff ≥ 0.9, no rain/mixed risk, previous day not rained on, no wind hold (`data.py:644-654`); quality from snowfall-weighted temperature `powder_temp_c` (good physics: `fetch_data_v2.py:2827-2835`) with the −8 to −18 C band for full cold credit matching the dendritic growth zone (`data.py:657-662`); calm gate at 40 km/h gust ≈ the ~10 m/s wind-packing threshold (`data.py:602,663`). Live proof the exclusions are real weather, not bugs (6 independent Open-Meteo cross-checks): Jackson Hole's 15.8 cm day correctly blocked at 76 km/h gusts (live check: 87 km/h); Nozawa Onsen's 38 cm blocked for 11 mm of real rain at +11 C the day before; Niseko's 23 cm report blocked for three consecutive rain days at +1 to +4 C. Every hand-recomputed gate decision matched the code's output exactly.

**The forecast path works end-to-end.** On the 12:12Z file, Palisades Tahoe day 3 lists in the forecast group: 11.6 cm, ff 0.916, tp=1, wp=1, label "powder", model agreement passed. The pipeline can produce a powder call when the data lets it.

**Nothing over-calls.** The falsifier threw wet storms, rain-on-snow, implausible reports (the 2× depth rule at `powder.py:201` multiplies, never divides — depth 0 safely blocks), missing depth, and unit confusion at the system; every attack was blocked. The system's failure mode is silence, not lies.

## What is wrong or unproven (severity-ordered, each with its fix)

**1. CRITICAL — the fallen-snow groups are structurally dead.** `day_point` nulls every past-day field except snowfall/rain/precip (`fetch_data_v2.py:2683-2686`, confirmed: `if past: ... p[k] = None`), and `derive_day` returns an all-null derived block for past days (`fetch_data_v2.py:2745-2746`). The retroactive gates require exactly those fields: cold needs `powder_temp_c` + `temp_max_c` (`powder.py:172-177`), thaw needs `temp_max_c` (`powder.py:179-183`), wind needs `gust_max_kmh` (`powder.py:185-189`), and any missing gate drops the row (`powder.py:222-225`). Live: 0 of 258 past days across all 86 resorts have any of these fields; all 7 candidates with ≥20 cm in 72 h were rejected, 3 of them for "no data for cold, thaw, wind". This is doc item 6, flagged BLOCKING on 27 Nov, unimplemented. **Trap confirmed by cross-check: item 6 as written does not fix it** — it says derived fields stay null on past days, but the cold gate reads `derived.powder_temp_c` (`powder.py:172`). *Fix: keep `temp_max_c`, `temp_min_c`, `gust_max_kmh` on past days in `day_point`, AND compute `powder_temp_c` for past snowy days from the `past_days` hourly data (or change the cold gate to band temps only).*

**2. CRITICAL — "powder today" is structurally impossible.** `powder_score` requires the previous day's `rain_risk` to be a bool (`data.py:643`); for day 0 that is index −1, a past day whose derived block is null. All 86 resorts' day-0 scores are None for this reason, including Mt Hood Meadows (21.1 cm) and Timberline (25.4 cm) on the morning file. Doc item 3, unimplemented. *Fix: compute `derived.rain_risk/mixed_risk/phase` for index −1 with the same hourly rules (`past_days=1` on the hourly call suffices).*

**3. MAJOR — the fixed 7:1 ratio under-calls cold powder through the amount gate.** The 10 cm gate (`data.py:596,646`) is applied to 7:1 centimetres, so it demands ≥14.3 mm of water regardless of temperature. Real snow-to-liquid ratios: US mean ~13:1, cold low-wind storms 15-30:1 (Baxter et al. 2005; Roebber et al. 2003). Morning file: Aspen Snowmass day 1 (9.5 mm at −8.7 C → shown 6.7 cm, realistic 11-14 cm) and Big Sky day 1 (10.7 mm at −10.1 C → shown 7.5 cm, realistic 13-16 cm) both rejected by the amount gate; both pass at realistic ratios. Direction is strictly an under-call — quality labels come from temperature, so the ratio never fakes powder, it hides it, and the coldest (best) storms are hidden most. *Fix: upgrade 1 below, or as a one-liner lower the amount gate to a water threshold (~7 mm) when `powder_temp_c ≤ −8 C`.*

**4. MAJOR — no measured-refutation gate on the forecast group.** `forecast_row` (`powder.py:251-274`) never consults `recent.measured`; the model-vs-sensor check exists only in `best_ski_index` (`data.py:478-488`). Live near-miss: Timberline's model says 25.4 cm on day 0 while the resort reports 0.0 cm — today it is blocked only incidentally (by defect 2 and model disagreement). Once defect 2 is fixed, a model dump the resort's own sensors refute can list as powder. *Fix: in `forecast_row`, when index 0 and the measured 24 h figure is far below the model's day-0 snow, drop or demote the row.*

**5. MAJOR — up to ~36 h of the measured 72 h window is never judged.** Gates judge days −3..0 (`powder.py:74`), but a reading may be 36 h old (`powder.py:68`), so its 72 h window reaches ~108 h back. Live: Stevens Pass's reading was 28 h old, leaving ~24 h of counted snow outside every gate — rain or thaw in that span passes silently. *Fix: extend gate coverage to day −4, or cap the listed amount to snow attributable to days −3..0.*

**6. MAJOR — fresh resort reports dropped as "stale" when the depth comes from a station.** `reading_time` (`powder.py:130-134`) only trusts `depth.observed_utc` when the depth is a resort report from the same provider. Rusutsu reported 23 cm today, observed this morning, and was dropped as "stale" because its depth is a JMA station measurement. Doc item 4 names this case; unimplemented. Conservative (kills true positives only). *Fix: fetcher adds `recent.measured.observed_utc` for every kind; the page reads it directly.*

**7. MINOR — model agreement is checked at the summit while the listing speaks for the mid band** (`fetch_data_v2.py:3211-3214` vs `powder.py:265-266`): one model's low *summit* total suppresses a mid-band powder day (Timberline: mid 25.4 cm, compared summit values 36.8 vs 1.3), and a resort with no summit elevation can never list a forecast at all (`data.py:672-677` returns None, which `is not True` silently skips). *Fix: compare at the scored band, or treat None as "no comparison" rather than a hard block.*

**8. MINOR — the powder gates ship essentially untested.** No test exercises `fallen_gates`, `fallen_verdict`, `implausible`, `reading_time`, `forecast_row`, `models_agree_cm` or `powder_score`; a page rendered permanently empty raises no failure — which is exactly how defects 1 and 2 survived. *Fix: fixture tests asserting a synthetic clean cold storm DOES list, each gate blocks its own synthetic violation, and day 0 is scoreable once day −1 rain_risk exists.*

**9. MINOR — missing physics: no density measure, no sun-crust.** ff cannot distinguish 15:1 blower from 6:1 cement when both are 100% frozen (temperature is the only density proxy, and a −3.0 C storm still earns "powder"); strong sun crusts south aspects at sub-zero temp_max, and `day_point` already stores `sunshine_s`/`uv_max` (`fetch_data_v2.py:2680-2681`) that nothing reads. Cosmetic: cold snow wrecked by wind is labeled "heavy snow" (`data.py:603`) when the defect is wind.

## The two highest-value upgrades

**Upgrade 1: Kuchera variable snow-to-liquid ratio (with underground-level masking).** Formula (NOAA VLab; AMS Weather and Forecasting 38(10), 2023): let Tmax = the warmest temperature in the column from the surface to 500 hPa, in Kelvin. SLR = 12 + (271.16 − Tmax) when Tmax ≤ 271.16, else 12 + 2 × (271.16 − Tmax), floored at 0. Per hour: `snow_cm = frozen_mm × SLR / 10`, where `frozen_mm` is exactly what `hour_split` already computes. Fields to add to `HOURLY_VARS` (`fetch_data_v2.py:2300-2303`), verified live in today's API: `temperature_850hPa`, `temperature_700hPa`, `temperature_600hPa`, `temperature_500hPa`, plus their `geopotential_height_*` (or standard-atmosphere constants 1457/3012/4206/5574 m). **The mask is not optional:** at Jackson Hole (summit 3185 m), naive Kuchera including the 850 hPa level — 1450 m underground, reading +6.5 C — gave 1.5 cm at 0.4:1 for a storm Open-Meteo calls 30 cm; masked, 67.2 cm at 15.6:1. Only include a level when its height is at or above the band elevation. Worked examples from today's live data (summit band, next ~4 days): Myoko Kogen 84.5 mm frozen water → 59.2 cm at 7:1 vs 128.5 cm Kuchera (15.2:1); Jackson Hole 43.1 mm → 30.1 vs 67.2 cm (15.6:1); Stevens Pass 30.0 mm → 21.0 vs 40.4 cm (13.5:1). Free bonus: hourly SLR gives storm sequencing in one comparison — second-half vs first-half mean SLR ≥ 2 apart = right-side-up (light on dense, good) or upside-down (crust on fluff, bad). Today all three storms are right-side-up (Myoko 13.0→17.2). Caveat, stated plainly: Kuchera verified at only R² = 0.23, MAE 4.84 against observed SLR in western US mountains (Veals et al. 2025) — much better than a constant 7:1, not a solved problem. Run it alongside the 7:1 figure for a validation season before it moves any gate. Cobb needs vertical-velocity and ice-RH profiles Open-Meteo does not expose, and Roebber's neural-net weights are not public; neither is buildable. Kuchera is the only published method whose sole input Open-Meteo provides.

**Upgrade 2: post-storm wind-destruction window from gust data already fetched.** `wind_gusts_10m` is already downloaded hourly (`fetch_data_v2.py:2302`) but only collapsed to a same-day lift-hours max (`fetch_data_v2.py:2852-2854`). Nothing tracks wind *after* snowfall ends — what turns yesterday's powder into wind board. Rule: let t_end = the last hour with snowfall > 0; count hours in (t_end, next sunrise] with gusts > 40 km/h; flag `powder_wind_degraded` when ≥ 3 such hours or any gust > 60 km/h. Worked examples from today's hourly data: Myoko — the biggest totals on the roster — is DEGRADED (74 km/h during the fall, 3 post-storm hours over 40); Jackson Hole is PRESERVED (87 km/h during, max 6 km/h after — settled cold and calm); Stevens Pass INTACT (max 24 km/h throughout). Zero new API fields; the hourly gust series just has to survive the day boundary in `derive_day` (prev_day is already threaded through, `fetch_data_v2.py:2735`).

**Free follow-up: measured SLR from SNOTEL fields already in the file.** `swe_change_24h_mm` and `change_24h_cm` are stored today (24 of 89 stations with SWE). Measured SLR = depth change × 10 / SWE change: Crystal Mountain 14.9:1, Big Sky 7.5:1, Vail 4.9:1, Jackson Hole 2.9:1 today — settlement makes these lower bounds, but logging forecast-vs-measured pairs for a season is the only path to *verifying* any forecast SLR. Doc item 1 specifies the per-row `swe_mm` field; unbuilt.

## What we still cannot know from our data sources

True new-snow density: no station today has both new-snow depth and SWE change non-null (0 of 89 — SNOTEL gives water without new-snow, Japanese and European providers the reverse), so measured SLR is settlement-biased at best. Independent ground truth: our cross-checks hit the same Open-Meteo model family the file is built from, so they confirm faithful storage, not reality; only resort reports and SNOTEL break that circle, and they cover a fraction of the roster. The real rain-snow line: 84% of wet days use the fixed FL−250 fallback, and 44% of wet band-days sit within 150 m of it, so phase calls near the line carry real uncertainty either way. Sun crust by aspect: we store sunshine and UV but have no slope aspects. Forecast skill: until doc item 2 (keep each forecast as issued) lands, the file overwrites its own history and no score can ever be checked against what actually fell.

## Bottom line for chasing powder

Trust a listed powder day: the gates that produce one are real physics, verified against independent data, and nothing we tried could fake one. Do not trust an *empty* page as "no powder anywhere": until fixes 1 and 2 land, the page is blind to all fallen snow and to powder today, and the 7:1 amount gate hides roughly the coldest tenth of genuine powder days. The fix list is short, already specified in `docs/powder_fetcher_fixes.md`, and items 3 + 6 (with the `powder_temp_c` addendum above) revive two-thirds of the page.
